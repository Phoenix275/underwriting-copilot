## §1. P0 — Reclassify DOB mismatch: manual review, not auto-decline

**This reverses current behavior.** Today `dob_mismatch` is in the material-misrepresentation
set (`MISREP` in `src/dashboard.py:557`), so any DOB mismatch forces an auto-**DECLINE**
regardless of score. Per the 7/24 note:

> "DOB Mismatch is not an auto-decline — that is a manual review — flag with different
> indicator that data entry mistake."

### Requirement

1. **Remove `dob_mismatch` from the auto-decline (`MISREP`) set.** Only genuine fraud signals
   (e.g. `smoker_nondisclosure`, where the lab contradicts a sworn answer) remain
   auto-declines. A date typed wrong is a data-quality issue, not fraud.
2. **Introduce a distinct indicator** — a "Data discrepancy — verify" flag, visually
   separate from the red "Material Misrepresentation" treatment (e.g. amber/"verify" styling,
   not red/"declined"). It should read as *"a human needs to check this,"* not *"this person
   lied."*
3. **Route affected cases to manual review**, letting the composite score set the band as
   normal (green/yellow). The DOB flag rides along as a review note, not a band-changer.
4. **Preserve the red field/row highlighting** on the Application and Extraction tabs (the two
   mismatched dates should still be easy to find) — only the *decision consequence* and the
   *label* change, not the visibility of the discrepancy.
5. **Top-drivers card:** for these cases, the driver line becomes "Data discrepancy — DOB on
   form vs. ID does not match; verify before proceeding," not "Declined — material
   misrepresentation."

### Cases this changes (known today)

- **APP-1049 (Aisha Nguyen), score 24** — was auto-declined for DOB mismatch → becomes a
  **green/manual-verify** case with a DOB-discrepancy flag.
- **APP-1013 (Linda Mensah), score 40** — was auto-declined → becomes **green/manual-verify**
  with the flag.

Both should now land in the review queue (or auto-approve with a verify note, depending on
final routing choice) rather than the auto-declined pile. **This is a decision to confirm with
the presenter before shipping**, because it directly changes the demo narrative for those two
cases.

### Ports required (the invariant)

Because scoring logic is duplicated, this change touches **both** engines:
- `src/dashboard.py` — the deployed dashboard's inline JS (`MISREP`, `recomputeVerdicts`,
  `decideJS`, `topDriversHTML`, conflict labels).
- If `src/engine.py` treats `dob_mismatch` as a hard override anywhere, port it there and to
  `web/src/lib/score.ts`, then run `npm --prefix web run verify` (CI enforces parity).

## §2. P1 — Underwriting chatbot for quick-answer questions

> "Start developing chatbot for quick-answer questions."

### Intent

An in-app assistant an underwriter can ask plain-English questions and get grounded,
case-aware answers — reducing hunting through tabs.

### Requirement (scoped for the POC)

- **A chat panel** available inside a case file, seeded with that case's extracted record,
  score breakdown, conflicts, and requirements.
- **Answers must be grounded** in the case data — same discipline as the existing
  `summaries.py` groundedness check. If the answer isn't supported by the case record, say so
  rather than guessing. No free-floating medical/financial advice.
- **Suggested starter questions**, e.g.:
  - "Why is this case in manual review?"
  - "What evidence is still outstanding, and what would each item cost/take?"
  - "What are the top three risk drivers here?"
  - "Is there a conflict between the form and the medical evidence?"
- **Scope guardrails:** it explains *the case and the product's own logic*; it does **not**
  make the decision, and it never invents a field the extractor didn't produce.

### Model note (ties to the extraction question)

The chatbot is the one place a genuine **LLM (Claude via the Anthropic API, gated behind
`ANTHROPIC_API_KEY`)** fits — same pattern as `summaries.llm_summary()`. Extraction stays
rule-based (see §3); the chatbot is a *reading/explaining* layer on top of already-structured
data, so groundedness is enforceable.

**Open question to resolve first:** does the demo run with a live API key, or must the chatbot
degrade to a scripted/templated fallback for an offline demo? (Mirror the summaries fallback.)

## §3. P1 — Handwritten / scanned document extraction

> "Try to be able to extract handwritten docs — and push through process."

### Today's reality (be honest in the deck)

Extraction is **deterministic, not AI**: `LocalTextExtractor` in `src/extract.py` uses
`pdfplumber` + regex/label-anchored parsing + checkbox-rect detection. It works because the
synthetic packets are clean **text** PDFs. It cannot read handwriting or scans.

### Requirement

- **Wire the existing `DocumentAIExtractor` stub** (`src/extract.py:135`) to a real OCR/entity
  service (Google Document AI is the documented target) so handwritten and scanned forms map
  into the **same output schema** `LocalTextExtractor` returns. The rest of the pipeline is
  unchanged by design.
- **"Push through process"** = once extracted, a handwritten packet flows through the identical
  conflict screen → scoring → routing as a text packet, with **no special-casing downstream**.
- **Surface extraction confidence**: OCR on handwriting is probabilistic. Low-confidence fields
  should be flagged for human verification (ties naturally to the §1 "verify" indicator) rather
  than silently trusted.

### Sequencing

This is a real integration (GCP processor, credentials, cost) — **POC-plus, not demo-week**.
For now: keep the stub documented, and in the deck present it as the concrete production
upgrade path, not a shipped feature. See §6 for the carrier questions that gate it.

> "Look at retinal scans — ask companies if upcoming trend or not prevalent throughout

**Explicitly a discovery item, not a build item.** Retinal-image risk signals are an emerging

carrier** (see §6) whether this is on their roadmap before spending any build effort. Do **not**
add a retinal-scan feature to the product speculatively.

## §5. P2 — ACORD schema alignment & API-key posture

> "401 and 402 existing API keys — 401 is in and 402 is to update back to MID — ACORD schemas
> standards for North America."

### Interpretation (confirm with the team)

- The pilot should speak **ACORD** (the North American insurance data-exchange standard) for
  integration, so extracted/scored records map to ACORD fields rather than a bespoke schema.
- Two API keys are in play: **401** (in use / inbound) and **402** (to be updated to route back
  to MID). This reads as an integration/credentials task on the backend/data-exchange side, not
  a UI change.

### Requirement

- **Document the field mapping** from our `extracted_record` schema (`src/extract.py:9–13`) to
  the relevant ACORD entities as the integration contract.
- **Treat 401/402 as environment/credential config**, not code constants — keys belong in
  environment/secrets, never committed.
- Flag the exact ACORD version/standard with the carrier before mapping (see §6).

## §6. Discovery — open questions for UHC (NOT buildable yet)

These are carrier-discovery questions from the notes. They **inform** the roadmap; they are
**not** requirements to build, and the product must not fabricate answers to them.

**Workflow & integration**
- End-to-end parameters to integrate the pilot into the company's workflow — today the pilot is
  a *single step*; what does the full lifecycle look like on their side?
- What are their top-5 automation targets?
- How much of underwriting is already automated vs. still manual?
- Average time to approve one case today (needed for any ROI claim — flagged as the #1 thing to
  measure).

**AI landscape**
- How much AI automation is already built into their underwriting process?
- What problems are they trying to solve with AI?
- Which AI platforms/competitors do they see integrated with underwriting?
- What's on their underwriting-system roadmap?

**Regulatory**
- Region-specific AI regulatory challenges and how they navigate them (ties to our existing
  NAIC-bulletin / explainability story).

**Documents & data**
- Turnaround time to get documents from hospitals/brokers.
- How they currently handle handwritten healthcare forms (gates §3).
- Whether retinal scans are an upcoming trend or not prevalent (gates §4).
